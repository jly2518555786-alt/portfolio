我的理解 · 跨学科映射

Prompt 让我想到语言学中的准确表达；Context 让我想到信息科学中的筛选与组织；Harness 让我想到控制论与制度设计；多 Agent 协作让我想到管理学中的分工与复核。

Skills 的分类与触发涉及分类学，但它还包含操作步骤、资源和执行方法。Loop 则提醒我：目标管理必须落实到反馈与停止条件。

这些映射是我的学习工具，并非学科之间的等号。这里也不把几种方法描述为严格、统一的嵌套标准或必然的技术演进路线。

Prompt engineering先定义问题，再改进表达

本章链接

提示词把意图转化为模型可以处理的任务描述。改进它，需要知道什么算是一个好结果。

“A clear definition of the success criteria for your use case”Claude 官方文档 · Prompt engineering overview · Before prompt engineering

我优先关注的五件事

  1. 任务：需要解决什么具体问题？
  2. 背景与角色：面向谁、在什么场景、采用什么专业视角？
  3. 输入与范例：哪些是材料，哪些是期望的成品？
  4. 输出要求：需要哪些内容、结构和证据？
  5. 验收：如何判断结果合格，材料不足时如何处理？

看一个表达逐步清晰的例子

帮我比较这两个产品。

比较的目的、依据与输出结构仍不明确。

面向准备选型的业务负责人，比较附件中的两个产品。
按适用场景、核心能力、部署要求、维护成本四个维度整理。
只使用附件材料；未披露的信息标为“待确认”。
输出一张对照表，并附每项判断的材料出处。
将已披露事实和你的推断分开。
列出影响选型、但材料尚未回答的三个问题。
检查：四个维度是否齐全？每项事实是否有出处？
我的理解 · 从成品倒推要求

找到一个好的成品范例，让 AI 倒推它背后的结构、信息要求和表达规则，并解释每条提示的作用。随后换一组输入测试，观察它能否复现关键特征。

指定“专家角色”不能替代真实资料与验证。反向提示得到的是候选方法，仍要用不同输入检验。

Context engineering在需要的时候，提供需要的信息

本章链接

上下文工程关心当前推理可见的信息：哪些需要进入、哪些可以检索、哪些应当保留或压缩。

我把它拆成三个问题：信息在哪里？什么时候需要？用什么形式交给模型？任务说明、检索片段、工具返回和历史记录，应围绕当前目标组织。

进入当前上下文

任务目标、关键约束、正在使用的证据、当前状态和必要的工具说明。

留在外部，按需读取

完整文档、历史日志、可复用知识、原始数据和暂时无关的任务材料。

RAG、记忆、压缩分别做什么？

机制用途需要检查
RAG从外部资料检索相关内容，再提供给模型。是否漏检、证据是否相关、来源是否可靠。
记忆跨步骤或跨会话保留状态、经验或偏好。是否过时、是否冲突、是否混入未经确认的结论。
上下文压缩用较精炼的记录接续长任务。是否保留目标、约束、决策依据和未完成事项。
我的理解 · 工作纪要也是信息接口

好的接续记录应当说明：目标是什么、已经确认什么、为什么这样决定、下一步还缺什么。这样新一轮执行才不需要重新猜测。

稳定信息与缓存

把可复用的稳定内容与经常变化的任务信息分开，有助于管理上下文。使用前缀缓存时，需要关注内容与序列化顺序的稳定性；是否命中还取决于具体服务的规则。

“一个任务一个会话”“更多使用 CLI”可以作为工作习惯，不是普遍最优规则。跨任务共享状态的需求、工具返回体积和权限要求都会影响选择。保留坐标与表格结构时，也不能只追求把 PDF 压成最短文本。

Harness Engineer核心：约束先行

本章链接

模型之外，还需要一套让它能够行动、留下状态、接受检查的执行环境。

理解 Harness 时，我关注工具连接、权限边界、运行状态、日志与检查。模型给出一个行动建议，系统还需要决定是否允许执行、如何记录，以及如何观察结果。

事前引导 · Guides

任务规则、代码规范、工具说明和架构决策，为行动提供方向。

明确什么应该做、哪些条件必须满足。

事后检测 · Sensors

测试、Schema 校验、结果对照与人工复核，提供执行后的反馈。

观察实际发生了什么，以及结果是否符合要求。

我的理解 · 控制论与制度设计

规则设定类似前馈控制，检测与纠错类似反馈控制。管理系统时，我会同时问“怎样减少错误”和“错误发生后怎样发现并处理”。

规则体系：约束先行，类似于管理公司

我的理解是：管理一个 AI 工作环境，也需要把工作原则、项目制度、执行设施、专业能力、知识资料和工作记录分开组织。不同文件承担不同职责。

管理公司的类比AI 工作环境中的对应物负责什么
共同工作原则用户级 AGENTS.md跨项目适用的协作方式、通用偏好和工作约定。
公司与部门制度项目根目录、子目录的 AGENTS.md项目规范、测试命令、编码要求，以及模块的局部规则。
运行基础设施config.toml、MCP、Hooks配置模型与执行环境，连接工具，并在执行事件中进行检查或控制。
专业部门能力Skills封装专业知识、操作方法、配套脚本与可复用工作流。
公司知识库README、docs/、架构与设计文档提供背景、业务事实、设计依据和使用方法。
工作纪要memories、历史对话与任务记录保留经验、上下文和任务状态，帮助接续工作。

用户级：跨项目的默认约定与配置

位置主要内容理解方式
~/.codex/AGENTS.md全局工作原则、协作方式、通用偏好。为不同项目提供共同的工作基础。
~/.codex/config.toml模型、审批、沙箱和 MCP 等配置。设置个人默认的运行环境。
~/.agents/skills/个人可跨项目复用的 Skills。按需调用的通用专业能力。
~/.codex/memories/ 或 memories_v2/启用记忆功能后生成的状态与摘要；具体目录取决于版本与迁移状态。辅助接续工作的记录，不作为权威业务规则。

项目级：当前项目的制度、能力与资料

位置主要内容理解方式
项目根目录/AGENTS.md项目规则、目录规范、测试与构建命令。当前项目的共同工作约定。
项目子目录/AGENTS.md模块或子系统的局部要求。在适用目录内细化项目规则。
项目根目录/.codex/config.toml项目特定的运行配置。受信任项目可加载此层配置，覆盖相应用户默认项。
项目根目录/.agents/skills/适用于当前项目或团队的技能。与项目代码一起维护的专业流程。
docs/、README、架构与设计文档项目知识、背景与参考资料。根据任务读取，也可以由指令文件明确引用。

规则怎样组合？

“Files closer to your current directory override earlier guidance”OpenAI 官方文档 · Custom instructions with AGENTS.md · How Codex discovers guidance
全局工作约定先加载用户级指令，提供共同基础。
项目工作约定沿项目根目录到工作目录读取适用文件。
局部工作约定更接近工作目录的指令可覆盖前面的冲突内容。

因此，用户级文件更像全局默认约定；它不是永远高于项目文件的“最高层法律”。这套文件组合规则也不能越过系统、开发者指令或运行环境强制执行的限制。

路径与加载规则补充

默认位置中的 ~ 表示用户主目录；CODEX_HOME 可改变 Codex 配置与状态的位置。同一目录中优先检查 AGENTS.override.md，再检查 AGENTS.md 等候选文件。

按当前官方文档，用户级 Skills 的位置为 ~/.agents/skills/；笔记中的 ~/.codex/skills/ 可能出现在旧版或特定安装环境中。应以当前客户端的发现规则为准。

我的理解 · 制度要有执行机制

先写清规则，再决定哪些交给指令引导，哪些通过配置、工具权限、Hooks、程序校验和审批真正落实。就像管理公司，制度文件、业务资料和会议纪要都有价值，但承担的责任不同。

参考：OpenAI · AGENTS.mdConfig basicsSkillsMemories

规则需要落实到哪里？

自然语言说明表达意图；程序校验、权限配置和审批机制执行边界。比如“写入前必须通过检查”，可以由运行时拦截实现，而不只是放在提示词里。

多 Agent 场景中，执行与检查可以分工，但检查者仍需要明确标准和可核验的材料。多一个模型，并不自动等于多一份独立、正确的判断。

应用例子 · REITs 数据修改的边界

产品规划中，确定性公式可以自动重算；涉及业务含义的影响判断先形成待审核提案，批准后再执行。这是我的方案设计，实际落地需要相应的权限与审批实现。

Loop Engineering核心：定义目标

本章链接

持续执行的前提，是知道什么算完成、什么需要重试，以及什么时候应该停下来。

我用 Loop Engineering 指代对执行闭环的设计：把目标、行动、观察、修正与停止条件连起来。这是本知识库采用的工作框架，不假定它是一个具有统一规范的标准术语。

把“做好”改写成可以检查的条件

  • 完成标准：能用测试、数据对照或人工标准验证。
  • 边界条件：允许修改什么，哪些动作需要人工决策。
  • 失败处理：重试、降级、保留中间结果或交由人工处理。
  • 资源预算：限制轮次、时间或成本，避免无止境执行。

走一遍闭环

定义目标完成与边界
→
执行产生候选结果
→
检查发现缺口
→
修正 / 停止反馈决定下一步
定义目标

示例任务：整理一份产品对照表。每项事实需要出处；最多允许两轮修正。

预设的教学演示，无模型调用
我的理解 · 目标也需要分层

最终目标是交付可用成果；阶段目标是完成一个可检验的子任务。只盯着“生成了内容”，容易遗漏质量、边界与交付条件。

定时触发或事件触发决定何时启动任务；闭环则决定启动后怎样推进。遇到证据不足或高影响决策，交给人工也可以是一个明确的结束状态。

本章链接

Skill 把任务说明、专业知识与配套资源组织起来，让 Agent 在需要时使用。

在 Agent Skills 开放格式中，一个 Skill 以含有 SKILL.md 的文件夹为核心，也可以包含脚本、参考材料和模板。

形式主要回答可以怎样配合
Prompt这次任务是什么？提出任务，并补充当前输入。

我的理解 · 分类帮助触发，流程帮助执行

Skill 的名称和描述帮助判断什么时候用，正文和资源帮助决定怎么做。我会从“专业能力沉淀”和“工作流程规范”两个角度整理自己的 Skills。

经验如何进入下一版？

任务结束后记录失败情形，提炼改进提案，检查是否适用于同类任务，再更新版本并复测。一次偶然成功，不应立即变成所有任务必须遵守的规则。

Skills 的实际发现、加载与执行方式由客户端实现决定。它也不能替代运行时权限控制。

有效管理成本优化每个有效结果的总成本

本章链接

Token 账单只是成本的一部分。失败重试、等待、人工复核与长期维护，也需要计入。

一次有效交付的成本
= 模型与工具调用 + 重试 + 人工复核 + 维护

这是我的分析框架，用于提醒自己检查被遗漏的成本项，不是统一的计费公式。

策略适用情形需要保留的判断
文档预处理材料包含重复页眉、噪声或无关页面。不要丢失关键结构、图表和来源位置。
按需检索资料量大，单次任务只涉及一部分。用真实问题检查漏检与召回。
缓存稳定内容多次请求复用较长的共同前缀。关注命中条件、有效期与实际账单。
模型路由任务难度不同，质量要求可检验。以评测结果决定路由与升级条件。
确定性脚本计算、格式转换、固定校验。明确输入边界、错误处理与维护责任。
我的理解 · 信噪比与总账

更短的输入不一定更省钱。如果删掉必要信息导致多轮返工，总成本反而可能增加。我更关心每个合格结果花了多少资源。

API 是调用约定与接口

应用按接口要求发送请求，服务按约定返回结果。API 本身不是一台服务器，也不是某个模型。

直连模式：后端调用模型厂商提供的服务。密钥应由后端管理，公开静态页面不应包含服务密钥。

应用部署的云

承载网站、业务 API、后台任务等。比如应用运行在腾讯云。

模型服务所在的平台

提供推理访问。例如应用通过 AWS Bedrock 使用其支持的模型。应用部署与模型访问可以采用不同平台。

数据层也需要分工

业务数据库保存结构化事实、状态和版本记录；文档存储保存公告、附件与原文；检索索引帮助定位相关材料。向量检索是一种能力，不意味着要把关系型数据库整体替换掉。

我的理解 · 从职责理解产品

研究一个网关或 Agent 框架时，我会先问：它位于哪一层？接收什么输入？承担哪些控制？故障时影响什么？这样更容易理解它的价值与可替代部分。

自我复制的计算机程序信息、规则与搜索带来的启发

本章链接

这一章记录三个相互关联、但需要分别理解的主题：复制自身、规则驱动产物，以及通过搜索改进方案。

自我复制：程序也可以成为被处理的对象

程序既可以执行操作，也可以作为数据被读取、生成或修改。复制自身的描述、复制运行环境、部署新实例或自动改进能力，是不同的问题。我的笔记从这里延伸到对规则与信息的理解。

我的理解 · 信息的双重使用

我关心的是：同一份信息，能否既描述一个系统，又参与驱动它运行？这让我从“另外维护一份规则说明”，转向思考“让规则本身生成说明与结果”。

规则同时驱动执行与文档

可以把字段定义、来源、计算逻辑和规则版本组织成统一的规则源，由程序读取并执行，再据此生成业务说明。规则修改后，检查哪些数据结果与文档需要更新。

这是规则驱动与一致性维护的设计思路，并不等同于程序自我复制。它对我的直接启发，是减少多处手工维护同一事实带来的偏差。

应用例子 · 从数据库生成最新 Excel

知识拓展：遗传算法怎样搜索？

遗传算法维护一组候选解，依据适应度评价进行选择，并通过交叉、变异等操作产生下一代，再继续评价与选择。候选如何编码、适应度如何定义，会直接影响搜索过程。

对 vibe coding 产品规划的启发

面对陌生问题，我可以先生成不同方向的候选方案，再按业务覆盖、实现成本、可验证性和维护难度比较，组合其中有效的设计，并通过原型检验。

“生成多个方案再评价”只是借鉴搜索思想。只有进一步定义编码、种群、选择、交叉与变异等机制，才是在实现遗传算法。评价标准本身仍需要审视；强化学习与遗传算法也不能简单视为同一种方法。
